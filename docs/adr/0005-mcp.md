# ADR 0005 — Our own MCP servers, reached through MCP clients in-process

**Status:** accepted

## Context
Tools must have strict schemas and per-agent allowlists, and be reusable outside NEXUS.
Spawning a stdio subprocess per tool call is slow. Two processes opening one embedded
ChromaDB leave each other's index stale (learned on a previous project).

## Decision
- Seven `MCPServer`s (mcp 2.x): workspace, sandbox, knowledge, tickets, notify,
  observability, demo.
- The backend talks to them through MCP `Client`s over the SDK's in-memory transport:
  the full protocol (initialise, `tools/list`, `tools/call`) with no subprocess per call,
  and only one process opens Chroma.
- `python -m nexus.mcp_servers <name>` serves any of them over stdio for external MCP
  clients (with the backend stopped if you serve `knowledge`).
- We do not use `langchain-mcp-adapters`. Our agents call tools through the hub, which
  adds allowlists, workspace injection, events, retries and the call log.

## Consequences
- Fast calls with real protocol behaviour; the Tools shows real health and call logs.
- Adding a server takes a `build(deps) -> MCPServer` function and one line in
  `hub.BUILDERS`.
